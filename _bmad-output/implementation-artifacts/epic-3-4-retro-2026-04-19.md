## What Went Well
1. **Complete user journeys delivered** — Greek symptom input → triage results with medical disclaimer → doctor redirect → live nurse dashboard. Full end-to-end, no gaps.
2. **Clean frontend architecture established** — `types.ts` as single source of truth, `api.ts` for all fetch calls, component composition, `@/` imports, no global state. Story 3.1 set the pattern; every subsequent story followed it.
3. **Elegant backend patterns** — `asyncio.Event` SSE signaling with `asyncio.shield` for concurrent client support, three-tier fallback chain, bounded deque with cursor-based streaming.
4. **Consistent review quality gate** — avg 3.3 patches caught per story (3, 3, 0, 3, 4), all resolved before marking done.
5. **Strong NFR9 compliance** — Greek throughout both patient and nurse interfaces after Story 3.1 cleanup.
6. **Efficient scoping in Story 3.3** — recognized that implementation was already complete from Stories 3.1/3.2; delivered with a single-line fix.

## Challenges and Friction
1. **Accessibility contrast issues recurred** — MTS badge contrast failures found in Stories 3.2 and 4.2 (2/5 stories = 40%). Caught in review both times, not during implementation.
2. **Complete absence of frontend automated testing** — no test framework in `package.json`; Story 4.2 explicitly marked test task as skipped. All 5 frontend stories verified manually only.
3. **Inherited code debt** — Story 3.1 required a full rewrite of existing `page.tsx` (monolith with hardcoded URLs, missing `patient_id`, English text, `any` types). Story 4.1 discovered 3 pre-existing bugs (tier 3 queue append, missing `import os`, hanging test).
4. **Edge case handling gaps** — empty env var bypassing fallback (3.1), SSE event loss after queue saturation (4.1), duplicate entries after reconnect (4.2), missing SSE payload validation (4.2). 3/5 stories (60%).
5. **Environment friction** — npm install required mid-epic to fix incomplete `node_modules` (3.2); ROS pytest plugin conflict requiring workaround flag (4.1).

## Cross-Story Patterns Observed
- **Architecture discipline compounds:** The `types.ts` + `api.ts` + component pattern from Story 3.1 made Stories 3.2, 3.3, 4.2 significantly faster.
- **Review-led stabilization continues:** Same pattern as Epic 2 — substantial quality gains from review rounds, not first-pass implementations.
- **Stub-and-replace workflow:** Story 3.1 created TriageResult/Disclaimer stubs; Story 3.2 replaced them. Clean incremental delivery.
- **Contrast as a blind spot:** Two separate stories (3.2, 4.2) had contrast failures on MTS badges. Implementation consistently misses what review catches.
- **Pre-existing bug discovery rate:** 2/5 stories uncovered bugs from earlier epics (4.1 found 3 bugs, 3.1 found major architecture violations).

## Technical Debt and Deferred Work
1. **No frontend test framework** — no Jest, Vitest, or Testing Library configured. All frontend quality is manual verification. (Priority: Medium for production, Low for hackathon demo)
2. **RAG readiness signal gap** — `/api/v1/health` does not reflect corpus availability. System silently falls back to base LLM if seeding fails. (Priority: Low)
3. **Deferred item tracking** — no formal mechanism in sprint-status to track deferred items across epics. (Priority: Low)
4. **Frontend has no end-to-end test automation** — NFR2 (2-second SSE delivery) and NFR3 (<3s page load) verified manually only.
